# 06. ロードマップ・体制・リスク

## 1. 現実認識

AutoCAD は 40 年以上、Tfas は 30 年近い蓄積がある。**全機能の再現を目標に置いた瞬間にこのプロジェクトは失敗する。**

勝てる領域を選ぶ:

| 勝てる | 勝てない（当面） |
|--------|----------------|
| ライセンス費ゼロによる協力会社への浸透 | 部品ライブラリの網羅性（数万点規模） |
| 属性を落とさない相互運用（IFC/DXF の品質） | 30 年分の細かい作図コマンドの完備 |
| ブラウザで即開ける（インストール障壁ゼロ） | メーカーとの提携・サポート体制 |
| スクリプト・自動化・CI への組み込み | 教育・資格・人材市場 |
| バージョン差でファイルが壊れない保証 | 実績と信頼 |

**初期の戦略は「作図する CAD」ではなく「壊さずに開ける・変換できる・自動化できる基盤」から入ること。** 変換とビューアで信頼を得てから作図に踏み込む。

## 2. フェーズ計画

### Phase 0: 基盤（0〜6 ヶ月）

**目標**: コアモデルと DXF 往復が動く。GUI はまだない。

- `od-core`: Database、エンティティ、シンボルテーブル、Command/Transaction、Undo
- `od-geom2d`: 曲線、交点、オフセット
- `od-io-dxf`: R12〜R2018 の読み書き（未知要素の保持を含む）
- `od-cli`: `opendraft convert a.dxf b.dxf`、`opendraft inspect`
- 往復変換テスト基盤（F-206）を最初から CI に入れる

**完了条件**: 実案件由来の DXF 100 図面が往復して幾何・属性の劣化ゼロ。

> この時点で既に**単体で価値がある**（バッチ変換・図面検査ツールとして）。これが初期コントリビュータを集める燃料になる。

### Phase 1: 見える（6〜12 ヶ月）

**目標**: ブラウザで DWG/DXF が高速に開ける。

- `od-render`: wgpu バックエンド、バッチ化、BVH、線種のシェーダ生成
- WASM ビルド + Web シェル（ビューア）
- `od-bridge-dwg`: LibreDWG ブリッジ（読み）
- 計測・マークアップ・印刷/PDF

**完了条件**: 100 万エンティティの図面が 60fps でパン・ズームできる（N-01）。

> **ここで最初のユーザーが付く。** 「協力会社の誰でも URL を開けば図面が見られる」は、それ自体が現場の課題への回答。

### Phase 2: 描ける（12〜24 ヶ月）

**目標**: 2D 汎用 CAD として実用に達する。

- コマンドライン UI、オブジェクトスナップ、極トラッキング、グリップ編集
- 主要編集コマンド（F-009）、ブロック、XREF、レイアウト/ビューポート
- 寸法・文字（**日本語組版・縦書き・IME を最初から**）
- `od-solver`: 2D 幾何拘束
- `od-io-sxf`: SXF SFC/P21（国内案件への入口）
- スクリプト API（Python/JS）、プラグイン基盤

**完了条件**: 実務者が既存 DWG を開いて修正・印刷・返送する業務が完結する。

### Phase 3: 設備（24〜36 ヶ月）

**目標**: MEP ドメインの中核。Tfas 参照機能の第一波。

- `od-geom3d-lite`（スイープ）+ 3D ビュー
- `RouteSegment` / `Fitting` / `Port` / 接続グラフ、Spec ルールエンジン
- ルート作図、自動継手、単線/複線/3D 切替、機器ポート接続
- 干渉チェック（+ BCF 入出力）
- 拾い出し・積算
- `od-io-ifc`: IFC 入出力（IDS 自己検証つき）
- 部品ライブラリの仕組みと初期セット

**完了条件**: 設備施工図 1 枚を OpenDraft のみで完成させた事例が 10 件。

### Phase 4: 深化（36 ヶ月〜）

- 自動ルート探索、各種計算（風量・圧損・管径・電線）
- 電気設備一式（器具配置・自動配線・単線結線図生成）
- 平面 ⇔ 断面の連動生成
- 協調編集（`od-sync`）
- OCCT 統合による複雑ソリッド、隠線処理 2D 生成
- 部品ライブラリのメーカー連携

## 3. 最初の 90 日でやること

抽象論を避けるため、着手順を具体化する。

1. **週 1〜2**: リポジトリ初期化、Cargo ワークスペース、CI（fmt/clippy/test/cargo-deny/依存グラフ検査）、DCO 設定、ライセンス方針の明文化
2. **週 3〜6**: `od-core` の Database / Object / Entity / Transaction / Undo。**この設計を間違えると全部やり直しになるので、ここに時間を使う**
3. **週 7〜10**: `od-io-dxf` の読み込み（R2000/R2018）。実図面でひたすら壊れないことを確認
4. **週 11〜12**: DXF 書き出し + 往復テスト基盤 + `od-cli`。**動くものを公開して最初のフィードバックを取る**

**やらないこと**: この期間に GUI を書き始めない。レンダラを書き始めない。誘惑は強いが、モデルが固まる前の UI は必ず捨てることになる。

## 4. 体制

### 最小構成（Phase 0〜1）

| 役割 | 人数 | 必要スキル |
|------|------|-----------|
| コアアーキテクト | 1 | Rust、計算幾何、CAD データモデルの理解 |
| I/O エンジニア | 1〜2 | バイナリ形式のパース、DXF/DWG 仕様の読解 |
| グラフィックス | 1 | wgpu/WebGPU、レンダリング最適化 |
| ドメインアドバイザ | 1（兼務可） | **設備施工図の実務経験者**。これが欠けると必ず的外れなものを作る |

### 拡大期（Phase 2〜3）

+ UI/UX、MEP ドメイン開発、テスト/QA、ドキュメント/コミュニティ、法務レビュー（スポット）。

**最重要**: 設備実務者を**開発チームの内側に置く**こと。ヒアリングでは足りない。既存 OSS CAD が実務で使われない最大の原因は、細部の作法（寸法の見え方、線の重なり順、印刷結果、キー操作の連続性）が現場基準から微妙にずれることであり、これは実務者が毎日触っていないと検出できない。

## 5. 持続可能性

OSS CAD が枯れる典型パターン（LibreCAD_3 が長年プレビューのまま止まった事実を直視する）を避けるため:

| 施策 | 内容 |
|------|------|
| 商用サポート事業者 | Apache-2.0 により第三者が有償サポート・カスタム開発を提供できる。**プロジェクトはこれを歓迎し、認定制度を作る** |
| 部品ライブラリのホスティング | メーカーが自社部品を配布する場（レジストリ）。メーカー側にメリットがあるため協力を得やすい |
| 公共・団体からの資金 | 国内では電子納品（SXF）対応が公共性を持つ。BIM 推進系の助成との親和性 |
| ゼネコン・サブコンのスポンサー | ライセンス費削減の額が直接的な動機になる。**協力会社 100 社に配る費用**と比較すれば投資として成立する |
| 段階的な有用性 | 各フェーズの成果物が**単体で使える**（変換ツール → ビューア → 2D CAD → 設備 CAD）。完成を待たずに価値が出る |

## 6. リスク登録簿

| # | リスク | 影響 | 対策 |
|---|-------|------|------|
| R-1 | 部品ライブラリが揃わず実務で使えない | 致命的 | メーカー公開 CAD データの変換ツール、コミュニティ投稿、レジストリの早期構築。Phase 3 と並行して開始 |
| R-2 | DWG 書き出しが r2000 止まりで敬遠される | 大 | DXF を主経路として明示。LibreDWG へのアップストリーム貢献 |
| R-3 | コアモデルの設計ミスが後で露見 | 致命的 | Phase 0 に時間を集中。破壊的変更の余地を Phase 2 まで残す（1.0 まで安定を約束しない） |
| R-4 | GPL 隔離の法的評価が覆る | 大 | 早期に法務レビュー。DWG 機能を本体から完全に切り離しておけば、最悪ブリッジのみ切れる設計 |
| R-5 | 性能目標（100 万エンティティ 60fps）未達 | 大 | Phase 1 の早期にベンチマークを作る。未達なら描画方式を見直す時間を確保 |
| R-6 | 実務者の関与が得られず的外れになる | 致命的 | 実務者をチームに入れる。Phase 0 の変換ツールの段階から現場に配って使ってもらう |
| R-7 | 開発者が集まらない | 大 | Rust + WebGPU + CAD という技術的魅力を打ち出す。Phase 0 の時点で「単体で有用な CLI」を公開し、貢献の入口を作る |
| R-8 | 商標・知財のクレーム | 中 | 商標を使わない、クリーンルーム維持、DCO、法務レビュー |
| R-9 | OCCT 依存が WASM ビルドを重くする | 中 | `od-geom3d-lite` で大半を賄い、OCCT は遅延ロードの任意依存にする |
| R-10 | 「機能を増やす」圧力で焦点が拡散する | 大 | 非目標（[01 §1](01-requirements.md#非目標明確にやらないこと)）を明文化して守る。ドメインはプラグインで外に出す |
