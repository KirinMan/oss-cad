# 02. アーキテクチャ

## 1. 設計原則

1. **コアは UI を知らない**。ドキュメントモデル・幾何・ソルバ・I/O は GUI ツールキット非依存。LibreCAD_3 が正しく目指し、LibreCAD 2.x が果たせなかった分離を最初から守る。
2. **単一のドキュメント、複数のビュー**。2D 単線図、2D 複線図、3D、断面、集計表は同じデータの投影である。同期処理を書かないで済むよう、派生を常に導出する。
3. **ドメインはコアの拡張機構の上に載る**。MEP はコアを改造せず、拡張属性とカスタムエンティティで実装する。MEP を特別扱いした瞬間、次のドメイン（構造、土木、電気盤）が載らなくなる。
4. **未知のデータを壊さない**。読めない要素は原形のまま保持し、保存時に書き戻す。バージョン差による情報喪失は最大の実害。
5. **すべての編集はコマンド**。GUI 操作・コマンドライン・スクリプト・プラグイン・協調編集はすべて同じコマンドオブジェクトを経由する。Undo と履歴と同時編集がこの一点に集約される。

## 3. 技術選定（ADR）

### ADR-001: コア実装言語は Rust

**決定**: `od-*` クレート群を Rust で書く。

**理由**:
- CAD はメモリ安全性の要求が高い（巨大な相互参照グラフ、長時間セッション、クラッシュ = 作業喪失）
- 同一コードで **ネイティブ / WASM 両方** をターゲットできる。ブラウザ版とデスクトップ版でコアを二重実装しなくて済む
- `wgpu` によりネイティブ（Vulkan/Metal/DX12）と Web（WebGPU）の描画バックエンドが統一される
- FFI で OCCT / LibreDWG / IfcOpenShell の C++ 資産を利用できる

**却下案**: C++（既存 CAD 資産との親和は高いが、WASM 化・並行処理・依存管理で不利）、TypeScript のみ（数値計算性能と大規模データで不足）。

---

### ADR-002: B-rep カーネルは OCCT を FFI で使う

**決定**: 3D ソリッド演算は OCCT (LGPL-2.1 + 例外) を `od-geom3d` の背後に隠して使う。

**理由**: 実用水準の OSS B-rep カーネルは事実上 OCCT のみ。Rust ネイティブの Fornjot は**開発終了**しており、B-rep をゼロから作る難度を示す実例。`truck` は有望だが実績不足。

**設計上の防御**:
- `od-geom3d` は trait `SolidKernel` を公開し、OCCT 依存はその実装の内側に閉じる。将来 `truck` 実装へ差し替え可能にする
- MEP のダクト・配管は**大半がスイープ＋押し出し**であり、汎用 B-rep を必要としない。軽量な `od-geom3d-lite`（自前スイープ + 三角形メッシュ）を用意し、OCCT は「複雑ソリッド演算が要るときだけ」ロードする遅延依存にする。これによりブラウザ版の WASM サイズを抑える

---

### ADR-003: 2D 拘束ソルバは PlaneGCS 系アルゴリズムを Rust 再実装

**決定**: FreeCAD の PlaneGCS が採る方式（制約を残差関数系として定式化 → DogLeg / Levenberg-Marquardt で求解 → ヤコビアンの階数と残差から冗長・矛盾・過拘束を判定）を Rust で再実装する。

**理由**: PlaneGCS は LGPL であり、FFI 経由なら利用可能だが、C++ の大きな依存を WASM に持ち込みたくない。またドラッグ中のインタラクティブ求解（一時制約でカーソル追従しながら連続求解）はホットループであり、コアと同一言語で持つ利点が大きい。アルゴリズム自体は公知。

**構成**:
```
制約グラフ → 連結成分分解 → 部分系ごとに DOF 解析
          → 解析的に解ける部分（作図的分解）は直接解く
          → 残りを数値最適化（LM / DogLeg、スパースヤコビアン）
```

---

### ADR-004: 描画は wgpu、線分は GPU 側で展開

**決定**: `od-render` は wgpu 単一バックエンド。2D の線分・円弧はインスタンス化してコンピュート/頂点シェーダで画面空間の帯に展開する。

**理由と手法**（[00. 調査](00-research.md#4-レンダリング--実行環境) の知見に基づく）:
- ドローコール数が支配的ボトルネック → **同一マテリアル（画層色・線種・線幅）のエンティティを 1 つの大バッファにバッチ**し、`draw_indirect` で 1 コールに畳む
- CPU 側に **R 木 / BVH の空間インデックス**を持ち、ビュー変更時はフラスタムテストで可視バッチのみ提出
- 線種（破線・一点鎖線）は**弧長パラメータをシェーダに渡してパターン生成**。CPU 側でセグメント分割しない
- ズームアウト時は LOD: 画面上 2px 未満のエンティティを点群バッチに縮退させる
- 選択・スナップの当たり判定は CPU 側 BVH（GPU ピッキングは往復レイテンシがドラッグ操作に響く）

**目標**: 100 万エンティティで 60fps（N-01）。バッチ数を数百に抑えることが達成条件。

---

### ADR-005: UI シェルは Tauri（デスクトップ）+ Web（ブラウザ）、キャンバスは wgpu

**決定**: UI クロームは Web 技術（TypeScript + 軽量フレームワーク）で書き、描画キャンバスは Rust/wgpu が占有する。デスクトップは Tauri で同じ UI をラップする。

**理由**:
- CAD の UI は「大量のパレット・ダイアログ・プロパティグリッド・表」であり、Web の UI エコシステムが最も生産的
- Qt を選ぶと Web 版が別実装になる。二重実装は小規模チームには致命的
- ホットパスは Rust 側にあるため、UI クロームが DOM でも性能要件を満たせる

**リスクと対策**: DOM ⇔ Rust の境界がチャタリングすると重くなる。→ **境界を「コマンド送信」と「イベント購読」の 2 本に限定**し、ドラッグ中の高頻度更新は Rust 側で完結させる（UI は結果通知のみ受ける）。

**却下案**: Qt/C++（Web 版が作れない）、egui などの Rust GUI（複雑なダイアログ・IME・アクセシビリティで不利。**日本語 IME の品質は必須要件**）。

---

### ADR-006: すべての編集は Command として表現する

**決定**: ドキュメントへの変更は `Command` トレイトの実装を `Transaction` に適用する形でのみ行う。直接のミューテーションは `od-core` 内部に閉じる。

```rust
pub trait Command: Send {
    fn name(&self) -> &'static str;
    fn apply(&self, tx: &mut Transaction) -> Result<CommandOutcome>;
}
```

**これが同時に解決するもの**:

| 機能 | Command 経由で自然に得られるもの |
|------|------------------------------|
| Undo/Redo | トランザクションの逆操作を記録 |
| スクリプト API | コマンドを直接構築して実行 |
| 協調編集 | コマンドをネットワークに流す（意図が保存される） |
| マクロ記録 | コマンド列の記録・再生 |
| 監査ログ | 誰がどのコマンドを実行したか |
| 自動テスト | GUI なしでコマンド列を実行して検証 |

### ADR-007: プラグインは WASM コンポーネント

**決定**: サードパーティ拡張の既定は WASM Component Model（wasmtime）。ホスト API は WIT で定義する。

**理由**: ObjectARX 型のネイティブ DLL は強力だが、クラッシュがアプリを道連れにし、ABI 互換の維持が地獄になる。WASM ならサンドボックス、クロスプラットフォーム、バージョン耐性が得られ、**ブラウザ版でも同じプラグインが動く**。

**権限モデル**: プラグインは宣言した capability（ファイル読み書き / ネットワーク / ドキュメント書き込み / UI 描画）のみ許可される。

**逃げ道**: 性能が必要な用途（大規模解析）にはネイティブプラグインも用意するが、既定では無効。

---

### ADR-008: 独自ファイル形式 `.odc` を第一級とし、DWG には依存しない

**決定**: 保存の既定は独自形式 `.odc`（後述）。DWG/DXF は変換フォーマットとして扱う。

**理由**: MEP の属性・拘束・履歴は DWG の表現能力に収まらない。DWG を主形式にすると、LibreDWG の書き込み制約（r2000 まで）にプロダクトの表現力が縛られる。詳細は [03. データモデル](03-data-model.md)。

## 4. モジュール間の依存規則

- `od-core` は `od-render` / `od-app` / `od-io-*` を**知らない**（逆依存禁止）
- `od-domain-*` は `od-core` の公開 API のみを使う。`od-core` に MEP 固有の分岐を入れない
- `od-io-*` は `od-core` のモデルとの変換のみを担い、UI に触れない
- GPL 依存（LibreDWG）は **プロセス境界の向こう側**にのみ存在する

CI で `cargo-deny` と依存グラフ検査を回し、この規則の違反をビルド失敗にする。

## 5. 実行形態

| 形態 | 構成 | 想定用途 |
|------|------|---------|
| デスクトップ | Tauri + ネイティブ wgpu + 全プラグイン | 主戦場。施工図作成 |
| ブラウザ | WASM コア + WebGPU + 制限付きプラグイン | 閲覧・レビュー・軽編集・協力会社の即時参加 |
| ヘッドレス CLI | `od-cli` | バッチ変換、図面検査、CI での自動集計 |
| サーバ | `od-sync` + ジョブワーカ | 同時編集、干渉チェックの重い計算のオフロード |

**重要**: ブラウザ版とデスクトップ版は**同一のコア・同一のファイル形式・同一のプラグイン**。「Web 版は機能が違う」という状態を作らない。

## 6. 性能設計の要点

| 課題 | 手法 |
|------|------|
| 巨大図面のロード | エンティティのレイジーデシリアライズ。ヘッダ + 空間インデックスのみ先読みし、ビューポート内から実体化 |
| 再描画 | ダーティ領域追跡。変更されたバッチのみ GPU に再アップロード |
| 干渉チェック | BVH + 空間ハッシュで候補絞り込み → 精密判定は Rayon で並列化。増分更新（変更した部材の周辺のみ再判定） |
| 拘束求解 | 制約グラフを連結成分に分解し、影響のある部分系のみ解く |
| Undo | 逆コマンドを保持（スナップショットではない）。大規模操作のみスナップショット併用 |
| 自動保存 | 操作ログの追記書き込みで最大 30 秒分の損失に抑える（N-06） |
