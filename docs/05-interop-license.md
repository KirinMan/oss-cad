# 05. 相互運用とライセンス戦略

相互運用とライセンスは同じ文書で扱う。**両者が不可分**だからである。DWG を扱おうとした瞬間にライセンスと法務の制約が設計を規定する。

---

## 1. ライセンス設計

### 1.1 コアのライセンス: Apache-2.0

**決定**: `od-core` を含む主要クレートは **Apache-2.0**。

**理由**:
- 特許条項がある（CAD 領域は特許が濃い。BIM 関連の特許出願も多数存在する）
- 企業が採用・組み込みしやすい。**商用サポート事業者が育つことがプロジェクトの持続条件**であり、GPL はここで摩擦になる
- 既存 OSS CAD（LibreCAD: GPL-2.0、QCAD: GPL-3.0）が商用エコシステムを作れていない事実を踏まえる

**却下案**: GPL-3.0（LibreDWG をそのままリンクできる利点はあるが、企業採用と商用サポートの芽を潰す）、MPL-2.0（ファイル単位コピーレフト。妥協案としては悪くないが、特許条項が Apache-2.0 ほど明確でない）。

### 1.2 依存ライブラリのライセンス地図

| ライブラリ | ライセンス | 結合方式 | 判断 |
|-----------|-----------|---------|------|
| OCCT | LGPL-2.1 + 例外 | 動的リンク | ✅ 可。**静的リンクしない**ことを CI で検査 |
| IfcOpenShell | LGPL-3.0 | 動的リンク or 別プロセス | ✅ 可 |
| **LibreDWG** | **GPL-3.0** | **別プロセス + パイプ IPC** | ⚠️ プロセス分離必須 |
| PlaneGCS | LGPL-2.1 | **アルゴリズムを Rust 再実装** | ✅ コード流用しない（[ADR-003](02-architecture.md#adr-003-2d-拘束ソルバは-planegcs-系アルゴリズムを-rust-再実装)） |
| wgpu / wasmtime / nalgebra | Apache-2.0 / MIT | 静的リンク | ✅ |
| ODA Drawings SDK | 商用（$25k〜/年） | — | ❌ **採用しない** |

### 1.3 GPL 隔離の設計

```
┌─────────────────────────┐        ┌──────────────────────────┐
│ OpenDraft 本体          │  stdio │ od-bridge-dwg (GPL-3.0)  │
│ (Apache-2.0)            │◀──────▶│  ─ LibreDWG をリンク      │
│  ─ DWG 変換要求を送信    │  JSON  │  ─ DWG ⇄ 中間 JSON/CBOR  │
└─────────────────────────┘  +CBOR └──────────────────────────┘
       別実行ファイル・別配布物・独立して動作可能
```

- ブリッジは**独立して意味を持つ単体ツール**として設計・配布する（`od-bridge-dwg convert a.dwg a.json` が単独で動く）
- 本体はブリッジが無くても全機能が動く（DWG 入出力のみ利用不可）
- 通信は汎用の中間表現。LibreDWG のデータ構造を本体に露出させない
- 配布パッケージでもブリッジは別コンポーネントとし、GPL-3.0 の条件（ソース提供等）を独立して満たす

**この境界の妥当性は法務レビューを受けること。** 「別プロセスなら常に安全」という単純な話ではなく、通信の密結合度や配布形態が判断材料になる。ブリッジ単体で有用であることと、本体がそれ無しで完結することが、境界を支える論拠になる。

### 1.4 商標とクリーンルーム

- **「AutoCAD」「Tfas」「Rebro」は他社の商標**。プロダクト名・ドメイン名に使わない。「AutoCAD 互換」ではなく「**DWG/DXF 形式に対応**」と記述する
- リバースエンジニアリングによるコードのコピーを一切行わない。DXF は公開仕様、DWG は LibreDWG の既存成果（クリーンルーム実装）を利用する
- コマンド名・エイリアス（`LINE`, `L`, `TRIM`…）は**機能名であり創作的表現ではない**が、ヘルプ文書・アイコン・チュートリアルの文言をコピーしない
- コントリビュータには DCO（Developer Certificate of Origin）を要求。「業務で商用 CAD のソースを見たことがある人」の寄与について、由来の申告を求める

## 2. 相互運用

### 2.1 優先順位

```
第 1 層（自前実装・リファレンス品質）:  DXF, .odc
第 2 層（必須・OSS 依存）:            IFC, SXF(SFC/P21)
第 3 層（ベストエフォート）:           DWG（読み中心）
第 4 層（出力のみ）:                  PDF, SVG, STEP, glTF, PNG
```

### 2.2 DXF（F-201）

**自前実装**する。理由: 相互運用の生命線であり、外部依存の品質に運命を委ねられない。仕様は公開されており、[ezdxf](https://ezdxf.mozman.at/) の内部ドキュメントが実質的な一次資料として使える。

- 対応: R12 / R2000 / R2004 / R2007 / R2010 / R2013 / R2018、ASCII とバイナリ
- **未知のグループコードは `preserved/` に原形保持**し、書き戻す（[03 §5.2](03-data-model.md#52-互換性の契約n-04-の実装)）
- カスタムエンティティは、対応環境向けに XData を、非対応環境向けに**プロキシ図形（分解された線分群）を両方書き出す**

### 2.3 DWG（F-202）

- **読み**: LibreDWG 0.13.4 は r1.2〜r2018 を約 99% カバー。ブリッジ経由で利用
- **書き**: LibreDWG の書き込み対応は r1.1〜r2000 まで（r2004 以降は開発中）。したがって **DWG 書き出しは r2000 互換に限定**し、UI で明示する
- 実務上は「DWG で受け取り、DXF で返す」が現実解。ユーザーに正直に伝える
- 中長期の選択肢: LibreDWG の r2004+ 書き込み実装への**アップストリーム貢献**。プロジェクトにとって最も費用対効果の高い外部投資になりうる

### 2.4 IFC（F-203）

**最重要の相互運用経路**。調査で判明した現場の不満（IFC 書き出し品質が担当者スキルに依存、属性欠落）に真正面から答える。

| 項目 | 設計 |
|------|------|
| 対応 | IFC2x3 CV2.0 / IFC4 RV / IFC4.3 |
| 実装 | IfcOpenShell を利用（別プロセス or 動的リンク） |
| MEP 写像 | `RouteSegment` → `IfcDuctSegment` / `IfcPipeSegment` / `IfcCableCarrierSegment`、`Fitting` → `IfcFlowFitting`、`Equipment` → `IfcFlowTerminal` 他、`Port` → `IfcDistributionPort` + `IfcRelConnectsPorts` |
| 属性写像 | `XDataSchema.ifc_mapping` により**スキーマ定義時にマッピングが強制される**。マッピングのない属性はスキーマ登録時にエラー |
| 系統 | `IfcSystem` / `IfcDistributionSystem` として書き出し、接続グラフを保持 |
| 階・通り芯 | `IfcBuildingStorey` / `IfcGrid` |
| MVD 検証 | 書き出し後に IDS（Information Delivery Specification）で自己検証し、**不足を書き出し前に警告** |

**設定なしで正しい IFC が出る**ことを目標にする。「担当者のスキル依存」を設計で潰す。

### 2.5 SXF（F-204）

国内公共案件で必須。SFC / P21 の両形式に対応する。

- 仕様は公開されており（SCADEC / 国総研）、C の共通ライブラリも存在する。それを参照実装として Rust で書く
- 実運用の主流は **SFC**（P21 はファイルサイズが 3〜8 倍）。既定を SFC にする
- **レイヤ名規約の検査機能**を同梱（電子納品要領準拠。F-304 の検査ルールとして実装）
- SXF は表現能力が限定的（フィーチャコメント方式）なので、往復で失われる情報を**事前に一覧表示**してから書き出す

### 2.6 往復変換テスト（F-206）

**これを CI の一級市民にする。** 属性欠落は既存製品の最大の不満であり、ここで差別化する。

```
テストコーパス（各形式 100 図面以上）
  ↓ import
  ドキュメントモデル A
  ↓ export → import
  ドキュメントモデル B
  ↓
  差分検証:
    ─ 幾何: 対応するエンティティの座標差が公差以内
    ─ 属性: 全 XData フィールドの保持率（目標 100%、下限 99.9%）
    ─ 構造: レイヤ・ブロック・接続グラフの同型性
    ─ 見た目: レンダリング結果の画像差分（SSIM）
```

失敗はビルドを止める。テストコーパスは実案件由来のものを匿名化して集め、コミュニティで共有する。

## 3. 既存資産の移行

| 資産 | 移行手段 |
|------|---------|
| DWG/DXF 図面 | インポート。ブロック・XREF・レイアウトを保持 |
| AutoLISP スクリプト | 互換解釈系（F-302）。全網羅は目指さず、実測で頻出する API から対応 |
| ブロックライブラリ | 一括変換ツール。DWG ブロック → OpenDraft 部品 |
| Tfas / Rebro の図面 | **IFC 経由**（両製品とも IFC 入出力に対応）。ネイティブ形式の解析は行わない（法務リスク） |
| 社内標準・レイヤ規約 | 検査ルール定義（YAML）としてインポート |

**注**: Tfas のネイティブ形式（.tfs 等）の解析は、法的リスクとメンテナンスコストの両面から**やらない**。IFC / DWG を経路とし、必要ならユーザー側でエクスポートしてもらう。

## 4. セキュリティ

CAD ファイルは事実上「実行可能なデータ」になりうる。設計時点で対処する。

| 脅威 | 対策 |
|------|------|
| 悪意ある図面ファイル（パーサ脆弱性） | Rust による境界検査。**インポータは全て別プロセス or WASM サンドボックス**で実行し、結果のみを本体に渡す |
| 埋め込みスクリプト（AutoLISP の自動実行系マルウェアは実在する） | 図面内スクリプトは**既定で実行しない**。明示的な許可と署名検証を要求 |
| 悪意あるプラグイン | WASM サンドボックス + capability 宣言（[ADR-007](02-architecture.md#adr-007-プラグインは-wasm-コンポーネント)）。署名付きレジストリ |
| XREF による外部パス参照 | 相対パスの正規化、シンボリックリンク越えの禁止、ネットワークパスの明示的許可 |
| 部品ライブラリのサプライチェーン | 署名と再現可能なビルド。`rules.wasm` は capability 制限下で実行 |
| 協調サーバ経由の情報漏洩 | E2E 暗号化オプション、オンプレミス配布を第一級でサポート（**建設図面は機密性が高い**） |
