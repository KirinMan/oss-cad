# 04. MEP ドメイン設計（Tfas 相当）

## 1. このドメインの核心

調査で得た Tfas の最大の特徴は「**ルート（芯線）を引くと自動で立体化される**」ことである。オペレータの操作感は 2D 作図のまま、成果物として 3D モデルと属性が育つ。これが「3D CAD だから遅い・難しい」を回避しつつ BIM に接続できる理由であり、**設計の中心に据えるべき単一のアイデア**。

したがって、MEP のデータモデルは次の一点に集約される。

> **真実は「芯線 + 断面仕様 + 系統」。3D 形状も 2D 複線図も単線図も、そこからの派生である。**

形状を直接編集させない。形状は常に導出結果。これにより単線↔複線↔3D の切替が無損失になり（F-106）、サイズ変更が全ビューに即座に伝播する。

## 2. ドメインモデル

```rust
/// 配管・ダクト・電線管に共通する経路要素
pub struct RouteSegment {
    pub id: ObjectId,
    pub system: SystemId,          // 系統（給水・排気・電灯…）
    pub path: Centerline,          // 芯線: 3D 折れ線 + 曲率/勾配
    pub profile: Profile,          // 断面仕様
    pub spec: SpecId,              // 材種・接合方法・規格のセット
    pub insulation: Option<Insulation>,
    pub slope: Option<Slope>,      // 勾配（排水で必須）
    pub level: LevelId,            // 階
    pub ports: [PortRef; 2],       // 両端の接続先
}

pub enum Profile {
    Rect { w: Length, h: Length },       // 矩形ダクト
    Round { d: Length },                 // 丸ダクト・鋼管
    Oval { w: Length, h: Length },       // オーバルダクト
    Conduit { d: Length, kind: ConduitKind },  // 電線管
    CableTray { w: Length, h: Length },  // ケーブルラック
    Bus { rating: Current },             // バスダクト
}

/// 継手（自動生成される）
pub struct Fitting {
    pub id: ObjectId,
    pub kind: FittingKind,   // Elbow / Tee / Cross / Reducer / Cap / Flange / Union ...
    pub ports: Vec<Port>,
    pub generated_by: GenerationRule,  // どの規則から生まれたか
    pub overridden: bool,    // ユーザーが手で差し替えたか
}

/// 機器（ポンプ、AHU、分電盤、衛生器具…）
pub struct Equipment {
    pub id: ObjectId,
    pub part: PartId,               // 部品ライブラリ参照
    pub placement: Placement,       // 位置・向き・レベル
    pub ports: Vec<Port>,           // 接続口（種別・サイズ・向き・系統）
    pub properties: XDataMap,       // 能力・型番・メーカー・IFC Pset
}

/// 接続口
pub struct Port {
    pub owner: ObjectId,
    pub index: u16,
    pub frame: Frame3,              // 位置 + 接続方向
    pub profile: Profile,
    pub system_kind: SystemKind,    // 接続可能な系統の種別
    pub connected_to: Option<PortRef>,
}
```

### 接続グラフ

`Port` の接続によって、図面全体が**有向グラフ**になる。これが MEP を「線の集まり」から「システム」に変える。

```
Equipment(AHU) ─port→ RouteSegment ─port→ Fitting(Elbow) ─port→ RouteSegment ─port→ Diffuser
```

このグラフから直接得られるもの:

- **系統追跡**: 任意の部材から上流・下流を辿る（「この配管はどのポンプから来ているか」）
- **圧力損失計算**: 経路上の抵抗の積算
- **拾い出し**: グラフの走査による集計（F-111）
- **未接続の検出**: 次数 1 のポートを警告（施工図の致命的なミスの発見）
- **系統の色分け表示**: グラフの連結成分ごとに着色

## 3. 派生パイプライン

```
                  ┌──────────────────────────────────────┐
  ユーザー操作 ──→ │ Centerline + Profile + Spec + System │  ← 真実
                  └───────────────┬──────────────────────┘
                                  │ derive()
        ┌────────────┬────────────┼────────────┬──────────────┐
        ▼            ▼            ▼            ▼              ▼
   単線図(2D)    複線図(2D)      3D 形状     断面図       集計テーブル
   系統色の      外形線+         スイープ    切断面での    長さ・個数・
   1 本線        保温線+         ソリッド    投影         重量
                 中心線                       (F-114)
```

- 各派生は純関数 `fn(source, ctx, view_mode) -> Geometry`。テストしやすく、並列化できる
- 派生結果はキャッシュし、ソース変更時のみ再計算（ダーティ伝播）
- **平面と断面が常に連動**する（Rebro の強みとして知られる特性）のは、両方が同一ソースの派生だから。同期コードを書かない

### 継手の自動生成規則（F-103）

芯線の折れ点・分岐点・サイズ変化点に、`Spec` が定める規則で継手を挿入する。

```rust
pub struct SpecRules {
    /// 角度 → 使用する継手（例: 90° は 2 枚エルボ、45° はベンド）
    pub elbow_rules: Vec<AngleRule>,
    /// 材種ごとの最小曲げ半径（R = 1.0D など）
    pub min_bend_radius: BendRadiusRule,
    /// 分岐の作り方（Tee / 45°Y / サドル）
    pub branch_rules: Vec<BranchRule>,
    /// 径違いの扱い（同心 / 偏心レデューサ、偏心方向）
    pub reducer_rules: Vec<ReducerRule>,
    /// 直管の定尺長と継手位置（施工図で必須）
    pub stock_length: Option<Length>,
    /// 接合方法（溶接 / フランジ / ねじ込み / 差込）と必要離隔
    pub joint: JointSpec,
}
```

`Spec` は YAML で定義し、**ユーザーが編集・共有できる**。日本の施工基準（公共建築工事標準仕様書、SHASE-S、JIS）に沿った既定セットを同梱し、社内標準は差分で上書きする。**ここをハードコードすると国内実務で使えない。**

## 4. 主要機能の設計

### 4.1 ルート作図（F-101）

操作フロー:

1. 系統と仕様（Spec）を選ぶ（またはコンテキストから推定）
2. 始点を指示。**機器のポート上ならスナップして自動接続**（F-104）
3. 高さ（レベル）を指定。既定は系統ごとの標準高さ
4. 方向と距離を連続入力（極トラッキング + 直交モード + 数値入力）
5. 確定と同時に継手が挿入され、3D が生成される

**設計上の要点**: 高さの入力を「別のダイアログ」にしない。2D 平面で描きながら高さを流し込めることが、Tfas 型 UX の生命線。コマンドラインで `H=3200` のように途中変更できるようにする。

### 4.2 表示モード切替（F-106）

| モード | 用途 | 描画内容 |
|--------|------|---------|
| 単線 | 設計図・系統図 | 芯線 1 本 + 系統色 + サイズ文字 |
| 複線 | 施工図 | 外形線 + 保温線 + 中心線 + 継手記号 |
| 3D | 干渉確認・合意形成 | ソリッド |
| 隠線処理 2D | 図面出力 | 3D から生成した線画 |

同一の `RouteSegment` に対する `derive(view_mode)` の切替のみ。**データ変換を伴わない**ので瞬時かつ無損失。

### 4.3 自動ルート探索（F-107）

```
入力: 始点ポート, 終点ポート, Spec, 障害物集合, 選好ゾーン, レベル制約
   │
   ├─ 1. 3D グリッド化（ダクトスペース・天井懐を考慮した非等間隔グリッド）
   ├─ 2. 障害物のインフレート（保温厚 + 施工クリアランス + 支持金物）
   ├─ 3. A* 探索。コスト = 長さ + 曲がり数×α + レベル変更×β + 他系統との近接×γ
   ├─ 4. 経路の平滑化（不要な折れ点の除去、直線への吸着）
   └─ 5. 継手生成規則で実現可能性を検証（最小曲げ半径を満たさない折れは棄却）
出力: 経路候補 3 件（最短 / 最少曲がり / 最も既存ルートに沿う）
```

**重要**: 自動ルートは「提案」であり、必ず**人が選び、手で直せる**。全自動を目指すと現場で使われない。生成された経路は通常の `RouteSegment` になり、以後は手動編集と区別されない。

### 4.4 干渉チェック（F-108）

```rust
pub struct ClashRule {
    pub a: EntityFilter,        // 例: 系統=冷温水
    pub b: EntityFilter,        // 例: カテゴリ=構造
    pub kind: ClashKind,        // Hard(交差) / Clearance(離隔不足) / Duplicate
    pub tolerance: Length,
    pub severity: Severity,
}
```

処理:

1. BVH で候補ペアを絞る（`od-render` の空間インデックスを共有）
2. 精密判定を Rayon で並列化。ダクト・配管は掃引体同士なので**円柱/箱の解析的判定**で大半を処理し、複雑形状のみ OCCT のブーリアンに落とす
3. **増分実行**: 変更された部材の周辺のみ再判定。全体再計算は明示的な実行時のみ
4. 結果は `ClashIssue` オブジェクトとしてドキュメントに保存し、状態（未対応 / 対応中 / 承認 / 無視）と担当者・コメントを持つ

**BCF（BIM Collaboration Format）で入出力する**。他社の統合モデルツールと課題を交換できることが、ゼネコンの BIM コーディネータ（P3）にとっての実用条件。

### 4.5 計算（F-109）

| 計算 | 入力 | 出力 |
|------|------|------|
| ダクトサイズ決定 | 風量、推奨風速 or 等摩擦法 | 断面寸法（規格寸法へ丸め） |
| ダンパー自動選定 | 風量、ダクトサイズ | 型式・サイズ |
| 圧力損失 | 経路グラフ、部材の抵抗係数 | 全圧損失、必要静圧 |
| 管径選定 | 器具給水負荷単位 / 流量、許容流速・動水勾配 | 呼び径 |
| 排水管サイズ | 器具排水負荷単位、勾配 | 呼び径、必要勾配の検証 |
| 電線サイズ | 負荷電流、こう長、許容電圧降下 | 電線サイズ、保護機器 |

計算式・係数表は**プラグイン可能なルールセット**（YAML + WASM）にする。国・地域・団体基準ごとに差し替えられること。SHASE 基準と ASHRAE を両方同梱し、既定は前者。

### 4.6 電気設備（F-110）

配管・ダクトと同じ `RouteSegment` グラフに載せる（`Profile::Conduit` / `CableTray` / `Bus`）。加えて:

- **器具配置**: 個別 / 範囲均等割付 / 円弧配置 / 天井グリッドへのスナップ
- **自動配線**: 器具群と盤を指定すると、天井裏の経路に沿って配線を生成。条数を自動集計
- **回路管理**: 盤 → 分岐回路 → 器具のツリー。単線結線図を**同じデータから生成**（別図面として描かせない）
- **記号**: JIS C 0303 の構内電気設備記号を標準ライブラリとして同梱

### 4.7 拾い出し・積算（F-111）

接続グラフの走査で完結する。

```
集計軸: 系統 / 階 / 工種 / 部屋 / Spec / 施工区分
集計値: 直管長（定尺考慮）, 継手数（種別・サイズ別）, 機器数, 保温面積, 支持金物数, 塗装面積
出力:   CSV / XLSX / 独自テンプレート
```

- 集計定義は**保存できるビュー**とし、図面と一緒に配布する
- 図面と集計表は常に連動（表のセルから該当部材へジャンプできる）
- 積算ソフトへの連携は CSV マッピング定義で対応

### 4.8 シート機能 / 建築図の分離（F-113）

Tfas の「シート機能」に相当。建築図の差し替えで設備図が壊れないことが目的。

設計: **建築図は XREF として参照し、設備要素は建築要素への相対参照を持てる**。

```rust
pub enum Anchor {
    Absolute(Point3),
    /// 通り芯 X1 から東へ 500、Y2 から北へ 300、3FL から上へ 2800
    GridRelative { x_axis: GridId, dx: Length, y_axis: GridId, dy: Length,
                   level: LevelId, dz: Length },
    /// 建築要素（壁・スラブ）の面からのオフセット
    FaceRelative { host: ExternalRef, offset: Length },
}
```

建築図が更新されて通り芯やレベルが動いたとき、`GridRelative` で置かれた設備は追従する。動かしたくないものは `Absolute` を選ぶ。**どちらを既定にするかを系統ごとに設定できる**ようにする（現場ごとに流儀が違う）。

### 4.9 部品ライブラリ（F-112）

```
part/
├── part.toml        メーカー, 型番, 分類, 検索タグ, ライセンス
├── geometry/        3D 形状（パラメトリック定義 or メッシュ）, 2D シンボル（平面/立面/単線）
├── ports.toml       接続口の定義（位置・向き・サイズ・系統種別）
├── properties.toml  能力値, IFC Pset マッピング, 積算コード
└── rules.wasm       任意: サイズ選定ロジック
```

- **リポジトリ型の配布**（`opendraft-parts` レジストリ）。バージョン付きで依存解決する
- 図面には**使用した部品の実体を同梱**する（`resources/`）。相手が同じライブラリを持っていなくても開ける
- メーカー提供部品の受け入れ窓口を作る。ここは商用製品が持つ最大の資産（Tfas 15 で数万点規模）であり、**OSS が最も追いつきにくい部分**。初期は主要メーカーの公開 CAD データからの変換ツールと、コミュニティ投稿の仕組みで埋める

## 5. ドメイン層のコア非侵襲性

MEP の全要素は [03. データモデル](03-data-model.md) の拡張機構だけで表現される。

| MEP の概念 | コアでの表現 |
|-----------|------------|
| RouteSegment / Fitting / Equipment | `ObjectKind::Custom` + `CustomEntity` 実装 |
| 属性（能力・型番・施工区分） | `XDataMap` + 登録済み `XDataSchema` |
| 系統・Spec・部品 | `named_dict` 配下の辞書 |
| 3D 形状・複線図 | 派生グラフ（`derive()`） |
| 階・通り芯 | コアの `Level` / `GridAxis` テーブル（全ドメイン共通） |
| 干渉課題 | `ObjectKind::Custom`（BCF に写像） |

**`od-core` に MEP という単語を一度も出さない**ことを CI で機械的に検査する。この規律が、後から構造・土木・電気盤・プラント配管のドメインを載せられるかどうかを決める。
